Performance Optimization Points for Perihelion

1. Clipboard Instantiation:
In `copy_to_clipboard`, `arboard::Clipboard::new()` is called every time a user copies text or right after text is appended in auto-copy mode. Creating the clipboard instance typically performs system calls (like setting up COM on Windows) which can be expensive on the UI thread. Cache a single `arboard::Clipboard` instance in `PerihelionApp` instead of re-instantiating it.

2. File Writing during Downloads:
In `download_file_with_progress`, the file is written to using `file.write_all(&buffer[..n])?`. Wrapping the `std::fs::File` in a `std::io::BufWriter` will batch the write system calls, improving disk I/O performance significantly when downloading large model files.

3. Download Buffer Size:
The copy buffer in `download_file_with_progress` is relatively small (`[0u8; 8192]` / 8KB). Given that the model is around 1 GB, increasing this buffer size to 64KB or 128KB would reduce the CPU overhead of looping through read/write operations and event dispatches.

4. Event Parsing Overhead:
In `extract_perihelion_value`, creating a lot of matched elements or traversing a highly nested OSC bundle on every packet can take CPU time. Although not a primary bottleneck, limiting maximum bundle depth or optimizing match branches could be a structural improvement before the application scales.

5. Excessive String Allocation in Download Loop:
In `download_file_with_progress`, `filename.to_string()` is called inside the `while let Ok(n) = response.read(&mut buffer)` loop. For a 1GB file chunked at 8KB or 64KB, this forces thousands of unnecessary heap allocations per second. Convert `filename` to a `String` once before the loop and clone it, or change `DownloadEvent` to use `Arc<str>` or borrow the filename differently.

6. Channel Flooding and Unbounded Memory Usage:
The download loop sends a `DownloadEvent::Progress` over the `mpsc` channel for *every* read operation. This can easily flood the channel with hundreds of thousands of messages, overwhelming the UI thread. Consider throttling the progress updates (e.g., only send an update every 1MB, or track time and send an update every 16ms).

7. Collecting MPSC Iterators into Vectors:
In `handle_download_events` (which runs at the UI refresh rate, e.g., 60-144 times a second), the app calls `rx.try_iter().collect::<Vec<DownloadEvent>>()`. This allocates memory for a new Vector on the heap every single frame. It's much more efficient to bypass intermediate allocations using a simple loop: `while let Ok(event) = rx.try_recv() { match event { ... } }`.
